Part one

The seven things we can detect

Every captured action reduces to one of these. Everything downstream — sequencing, scoring, the graph — is built only from this vocabulary.

VerbWhere it comes fromWhat it recordsCoverage
focusAny app (OS)App name + window title — which usually carries the file name or email subjectAll apps

The asymmetry that matters

Inside a web app we see individual clicks and fields — real in-app steps. Inside a native app (Excel, Word, Acrobat) we currently see only the window title. That single fact explains almost every gap below.

Net result

The pipeline reconstructs the full skeleton — every app, every file, the order, the hand-offs, the send — as a single flow scoring 77/100. What it misses is the substance inside Excel, Word and the PDF: the formatting, the formulas, and above all the searches that join the files together.

Part three

When does a flow end?

This trace exposed a real bug, now fixed. It's worth understanding because it's the rule that decides what "end-to-end" even means.

Before — split on a 45s event gap
4 fragments
  • mail → excel (score 53)
  • mail in-app (76)
  • snippingtool → word (24)
  • word → excel (23)

Reading the PDF for five minutes looked like the task ending.

After — split on real idle
1 flow, seen 3×
  • 5 apps, 17 steps, score 77
  • mail → excel → acrobat → word

One coherent daily workflow, recognised as the same task across three days.

1

Real idle is the boundary

The logger tracks actual keyboard and mouse input. After 60 seconds with none, it writes an idle_start — that is a person stopping, and it ends the flow. Long pauses spent reading do not end it, because there is still input.

2

A 15-minute event gap is only a safety net

Used when idle wasn't recorded — an app crashed, the machine slept. Deliberately long, so it never cuts a working session.

3

One hour is the hard cap

A runaway guard so a single flow can't swallow an entire day if both signals fail.

Part four

Where screenshots belong — and where they don't

Screenshots are the fallback for apps we can't ask politely. They're the heaviest, most sensitive sensor, so they should be the last resort, not the default.

SurfaceBetter sensor available?Screenshot policy
Web apps
Salesforce, Gmail, internal tools		Yes — the extension already gives semantic clicks and fieldsNever Pixels would be strictly worse than the events we already have.
Excel / Word / OutlookYes — COM and UI Automation expose ranges, formulas, commandsOnly as backup Instrument properly; use pixels only if the API path fails.
PDF readers, legacy and proprietary desktop toolsNo — no scriptable surface at allYes This is the genuine use case: it's the only way to know what was on screen.
Password managers, banking, anything unlisted—Never Not on the allowlist, never captured.

Trigger on change, not on a clock

Capturing every 30 seconds produces mostly duplicates. The right trigger is a state change: the focused window changed, or the image's perceptual hash moved beyond a threshold. Each shot is reduced to an 8×8 hash so identical screens are detected deterministically — the same dialog on Monday and Tuesday hashes the same, with no AI involved. Status today: capture is built and off by default, but still timer-based, and the mining pipeline does not yet read the screenshots table.

Part five

Where AI sits

There is an explicit on/off switch. Everything above this line is deterministic and unchanged when AI is off.

AI off — the default
Fully deterministic
  • Capture, action log, sequencing
  • Normalization and clustering
  • Automatability score 0–100
  • Graph, rankings, admin console

No account, no key, no cost, no network.

AI on — layered on top
Interpretation only
  • Names the task in human terms
  • Explains what it accomplishes
  • Judges whether the boundaries are right
  • Sharpens the automatability ranking

Small model, runs on demand, cached per flow. Your own API key.

Why AI reads flows rather than events

By the time the model sees anything, the work is already done: actions captured, sequences cut, repeats collapsed, scores assigned. The model receives a compact list of normalized flows — not a raw event firehose — so it's cheap, cacheable, and swappable. It also gets the one job deterministic rules do badly: judging whether a sequence is really one task, which is exactly the failure mode Part three describes.

Part six

What it takes to capture your workflow in full

Three sensors close every red row in the trace. In priority order for this specific workflow.

A

Excel / Office automation — closes steps 4, 6, 8, 11

Excel's COM event model reports the exact range edited, the formula entered, the sheet and workbook, and every save — across all open workbooks at once. Crucially, the same interface that records these steps can replay them, so building the sensor is also building the front half of the automation.

B

UI Automation — closes steps 8, 9 and Word generally

The Windows accessibility layer reports which control was invoked and which dialog appeared — including the Find dialog and its search term. That search term is the join key between your report and the reference sheet, so it's the highest-value single field in the whole workflow.

C

File watching — closes step 2

Watching Downloads and your working folders links “clicked the attachment” to “opened this exact file”, and connects each file to the one saved from it. Cheapest of the three to build.

The honest bottom line

Today this workflow is detected as one correct end-to-end flow with the right shape — all five apps, the files, the hand-offs, the send — but with the in-app substance missing. That's enough to say “you do this every day and it looks automatable.” It is not yet enough to generate the automation, because the rules live in the formatting, the formulas, and the searches we can't see.
